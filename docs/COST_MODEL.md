# 成本模型

## 1. 为什么要单独写一页

"用 agent 帮你筛人"这件事的可行性完全取决于单位成本。如果每对候选都要跑一次大模型，万人会议的第一晚就会烧掉一辆车。这套实现的成本结构是硬的：

- **粗排零模型成本**：硬过滤走盲索引，召回走向量余弦（numpy，128 维）；
- **沙盒只跑"值得跑"的配对**：每人每晚 Top-K，按亲和度领票；
- **对话与评分用小模型**，只有已过门的配对才允许一次大模型调用（润色破冰句）；
- **每一笔都记账**：`cost_ledger` 记录 tier / model / tokens / usd，可出报表。

## 2. 实测数字（本机，2026-11）

引擎：`qwen3.6-35b-fast`（对话 + 评分），`nw-flash-flex`（仅破冰润色）。

一次干净的 12 场跑批（156 位候选人，10 对通过门控）按 tier 拆开：

| tier | 调用数 | tokens in | tokens out | 花费 | 占比 |
| :-- | --: | --: | --: | --: | --: |
| `small`（两轮对话） | 12 | 26,183 | 2,830 | $0.0056 | 11% |
| `judge`（结构化打分） | 12 | 18,205 | 2,089 | $0.0040 | 8% |
| `large`（破冰润色） | 10 | 8,216 | 2,200 | **$0.0425** | **82%** |
| 合计 | 34 | — | — | **$0.0521** | 场均 **$0.0043** |

**结论很反直觉：真正贵的是那句破冰话，不是对话本身。** 大模型的 token 单价比小模型贵 17 倍，而它只服务"已过门"的配对——占比却到 82%。

所以成本杠杆只有一个：`POLISH_WITH_LARGE_MODEL=false` 会让单场从 $0.0043 降到约 $0.0008（同样跑 12 场只要 ~$0.010）。代价是破冰句由 judge 模型来写，锋利度下降。要不要付这笔钱是产品判断，不是技术判断——默认开着，因为那是用户真正读到的那一句。

历史对照（不同批次、含多次重跑）：

| 场景 | 场次 | 门控通过 | 花费 | 场均 |
| :-- | --: | --: | --: | --: |
| 单场 QA（指定一对） | 1 | 1 | $0.0052 | $0.0052 |
| 夜间批处理（阈值 85） | 12 | 10 | $0.0521 | $0.0043 |
| 夜间批处理（阈值 87，未润色路径） | 24 | 3 | $0.0318 | $0.0013 |

## 3. 规模化推算

万人会议、会期 7 天、每人每晚 3 对（双向去重后约 1.5 万对/晚）：

```
场次总量            ≈ 10,000 × 3 × 7 / 2      = 105,000
单场成本（含润色）  ≈ $0.0043
沙盒总成本          ≈ $450
加 20% 重试/峰值    ≈ $540
```

即 **每人每会期约 $0.05**，比原始方案"7 天人均 $0.35"的假设还低一个量级（实测小模型比方案假设的便宜得多）。

如果关掉大模型润色，总成本降到 **$100 以内**。如果 judge 也换成贵模型（$2.5/M input），单场升到 $0.010–0.015，总量回到 $1000–1600，仍在可运营范围。

真正的成本风险不是单价，而是**配对数量爆炸**：`SANDBOX_MAX_PAIRS`、`pairs_per_user`、`topk` 三个参数必须显式设上限，默认值按万人量级定的。

## 4. 账本怎么读

```bash
curl -s localhost:8000/api/admin/cost -H "Authorization: Bearer <token>" | jq
```

```json
{
  "day": "2026-11-22",
  "total_usd": 0.2375,
  "by_tier": {
    "small": {"calls": 72, "tokens_in": 61000, "tokens_out": 9000, "usd": 0.0157},
    "judge": {"calls": 36, "tokens_in": 22000, "tokens_out": 3800, "usd": 0.0059},
    "large": {"calls": 8,  "tokens_in": 9000,  "tokens_out": 1200, "usd": 0.0350}
  },
  "sessions": 19,
  "avg_usd_per_session": 0.0125
}
```

要点：`large` 层调用数**必须**远小于场次数。如果两者接近，说明破冰润色被滥用，或者有人在循环里调用大模型——这是最值得设的告警。

## 5. 成本护栏（缺一个就会失控）

| 护栏 | 位置 | 默认 |
| :-- | :-- | :-- |
| 每晚最大配对数 | `SANDBOX_MAX_PAIRS` | 4000 |
| 每人每晚最大配对数 | `pairs_per_user` | 3 |
| 粗排召回数 | `SANDBOX_TOPK` | 20 |
| 模型并发 | `LLM_MAX_CONCURRENCY` | 8 |
| 单场超时 / 失败即弃 | `run_pair` 的 `finally burn()` | 是 |
| 大模型只给过门配对 | `SandboxConfig.polish_with_large_model` | 是 |

## 6. 与"确定性引擎"的关系

`LLM_MODE=deterministic` 时成本恒为 0，且**流程完全一致**：同样的过滤、同样的脱敏、同样的门控、同样的预算。这让 CI 与离线演示可以零成本跑通；也让"模型不可用"成为可接受的降级，而不是事故。

代价是对话质量：确定性引擎的文本来自按主题组织的模板（`llm/deterministic.py`）。它说得具体，但它不是那个特定的人。所以线上永远优先 live。
